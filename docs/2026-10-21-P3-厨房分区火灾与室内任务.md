# P3：厨房分区火灾与室内任务

日期：2026-10-21

## 已开放的操作流程

场景准备的新建入口现可选择「住宅厨房火灾」。配置住宅楼、楼层、东/西侧厨房与房门初始状态，三维进入对应剖面；也可直接点击厨房台面选房间。试算时刻变化后，烟气风险同步显示。

1. 选择厨房案例，创建草稿。该案例要求住宅楼，不要求充电棚。
2. 配置起火地址及人数，预览、保存、校验并发布。
3. 创建新场次并启动。室内烟感达到阈值后触发任务；室外机器人仍沿道路巡检，不会穿墙进入厨房。
4. 下达疏散与护送。若房门关闭，先通过「楼内烟气与门控」恢复通行，再预览路线。
5. 接收燃气任务、回执到位、等待处置时间并提交证据；核验后火势增长率降低。
6. 人员实际离开后可关闭房门，再提交房门核验任务。房内或门口有人时拒绝关门，护送员也参与检查。
7. 到集合点后，由居民代表或物业核验清点。历史回放保留当时的房门、烟气、任务和人员状态。

## 运行模型

### 明确的空间身份

火源地址为建筑对象 ID、底图版本、楼层、房间与稳定节点 ID。坐标由服务端从户型生成，客户端不能用任意坐标覆盖。新场次冻结地址和空间模型，修改准备参数不影响旧场次。

厨房案例将人口放在选定住宅中，每层两个厨房分区、最多八人。每人拥有独立起始站位，再经过房间中心、房门、走廊、楼梯、门厅、楼门和室外道路前往集合点。超过示例户型容量会拒绝保存和运行，不以重复堆叠人物扩充人口。

`spatial_units` 冻结水平比例与米制高程，层高 3.2 米、首层基准 0.18 米。人员路径长度、速度、任务高度和三维模型使用相同高程；历史世界没有该标记时保留原有显示换算。

### 分区烟气

`indoor_fire` 从冻结通行图建立房间、走廊、楼梯与门厅分区，仅在实际相连分区之间交换烟气。每 0.5 秒更新源项、分区交换和衰减；开门交换系数为 0.08，关门为其 0.02 倍。浓度使用 0–1 的训练规则量，限制在有效范围内。

门控事件在自身时间点改变交换条件，不会追溯修改先前浓度。时间线保留有界缓存，支持增量推进与历史读取。

模型用于比较处置顺序与疏散组织，是示例分区规则模型，不是 CFD 或实测建筑烟气预测。

### 同一状态贯通各功能

| 功能 | 实际使用的数据与效果 |
| --- | --- |
| 室内风险与画面 | 分区浓度驱动体积烟气、可见度和房间风险显示 |
| 人员暴露 | 按所在节点或正在经过的边插值累积，不再对整栋楼套室外烟气圆 |
| 风险路径 | A* 使用分区风险、容量和当前门状态，封闭房门不允许穿行 |
| 房门操作 | `indoor.door.set` 经统一命令应用服务，记录命令回执及不可变事件 |
| 安全校验 | 有居民、通行者或护送员尚未离开时，关闭请求被拒绝 |
| 燃气处置 | 完成到位、时长、文字证据要求后写入 `task.completed(kind=gas_off)`，降低后续增长率 |
| 房门任务 | 仅在起火房门确已关闭且其他提交条件满足时可核验 |
| 车辆 | 拒绝把室外喷水直接作用到任意厨房楼层；到场不代表室内灭火完成 |
| 智能体 | 规划预演读取实际通道状态；协调视图显示室内分区；不增加未经批准的自动门控 |
| 场景助手 | 对话上下文包含烟气与房门事实，引用 S9 来源；离线解读也可定位厨房风险 |
| 回放与分支 | 冻结世界与事件时间线驱动同一计算，不重建当时的火点或清零既有暴露 |

厨房烟感事件记录分区、楼层和浓度。任务激活继续兼容既有 `robot.alarm_confirmed` 事件类型，但明确记录 `source=indoor_detector`、显示「楼内烟感」为来源，不伪造机器人室内采样。

## 页面与建模

- 保留场景准备的步骤—三维—参数布局，增加楼层、房间、房门字段与台面点选，支持撤销。
- 三维增加厨房地面、橱柜、台面、炉灶、炉圈、烟罩、门板和分区烟气。
- 炉灶火焰位于实际楼层，室内关闭室外上升烟柱，烟气改由分区体积表达。
- 开门后的门板移到通行侧边；关门时才覆盖门洞，避免视觉上仍挡住通行路线。
- 自动进入剖面不弹出遮挡中心的通知。可切换楼层或恢复建筑外观。
- 导演台原工具栏增加「楼内烟气与门控」，打开原有处置任务抽屉；没有新增独立叠加面板。
- 门控区按楼层筛选，分区浓度与房门列表在抽屉内滚动；正文 16px、说明 14px、操作高度至少 44px。
- 厨房任务定位直接进入对应楼层，不将室内目标错误地定位到地面。

本阶段没有引入在线模型资产依赖；网络不可用不会阻止厨房设施和房门基础模型显示。

## 代码边界

- `schemas.scene`：两种参数契约与兼容 API。
- `fire_sources`：两种合法地址、楼层/房间及户型容量校验。
- `scenes`：厨房草稿的四项基础任务、版本派生。
- `spatial_world` / `exercise_world`：稳定室内节点、个人站位、米制空间和任务冻结。
- `indoor_fire` / `fire_environment`：确定性烟气与能源事件时间线。
- `spatial_simulation`：暴露、路径风险及门控通行。
- `indoor_commands`：房门授权、现场校验与事件写入，接入已有命令应用入口。
- `IndoorFirePanel` / `indoorFireVisuals`：门控工作区与分区模型表现。

新增 `PATCH /scenes/{id}/parameters`，接受两种参数结构；旧充电棚保存地址继续兼容。无需数据库迁移，不重写历史世界。

## 验证与自我拷问

13 项针对性检查通过，覆盖厨房合法地址、冻结、开关门烟气差异、楼层传播差异、路径恢复、连续移动、关门安全、燃气证据、历史回放、原案例兼容，以及 8 人实际疏散、重点护送和授权清点。前端类型检查与生产构建通过。

浏览器使用生产组件与隔离数据核对 1440×900、1366×650、390×844：厨房台面真实射线点选、列表/撤销/保存联动、门控列表与抽屉滚动；同时复核原充电棚点选。截图在 `output/playwright/kitchen-scene/`。

- **是否只是增加模板名？** 不是；地址、环境、任务、人员、命令与回放均有厨房路径。
- **关门是否只换颜色？** 不是；改变烟气交换、通道可达性，并产生可追溯事件。
- **有人会被操作悄悄困住吗？** 关闭请求检查当前房内和门口人员；初始关闭状态也明确提示需先开门。
- **是否用室外机器人假装完成室内处置？** 不会；室内烟感负责发现，机器人使用楼外接入点，处置证据来自实际参演任务链。
- **是否只验证局部动作？** 已运行从开门、分流、护送到集合点、清点和安全关门的完整人员链。
- **本轮是否已交付通用智能体任务图？** 没有；P4 才处理任务依赖图、资源预占、人工接管及重启恢复，不能以新状态文案代替编排实现。
