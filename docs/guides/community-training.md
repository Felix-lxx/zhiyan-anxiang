# 社区夜班：分户通知与有限人手

## 开启方式

场景准备 → 人员与出口 → 社区夜班训练，选择“夜班画像 · 分户通知与有限人手”。设置值守岗位（1–8）和场景种子后保存、发布，再创建新场次。相同空间、人数和种子生成相同画像；数据按匿名训练户组织，不是居民实测档案。

旧场次继续读取原冻结世界。未开启该选项的场景沿用原通知、环境及人员规则。

## 实际操作

1. 在导演台“当前任务”打开“通知到户，责任到人”。按楼栋、楼层或画像筛选；选中住户进入详情，返回保留列表筛选和页码。
2. 电话或入口广播先记录已发出通知，再由参演人员填写收到回执。需要到户时点击“派出值守员到户”，值守员沿服务端通行图前往户门。新世界须实际到门后才能提交敲门回执；到门不自动确认收到。广播覆盖不等于确认收到；需要直接联系的住户不能仅凭广播确认。
3. 收到回执只核实通知。总控随后比较方案或定位具体居民，安排撤离与重点护送；确认本身不自动下达移动命令。熟睡准备时间、行动速度与护送会合影响后续执行。
4. 岗位页显示正在承担的责任任务和护送对象。接收物业任务占用一个有限岗位；已有任务、实体护送及活动计划归属均影响再次接收。任务核验完成或撤回接收后释放岗位。
5. 手机参演登记后，在“现场回执”使用同一分户界面。提交会写入服务端事件，导演台通过实时通道更新；页面不预填成功状态。
6. 结束归档保存通知进度、回执、未确认户数和模拟条件。历史回放按当时时刻恢复，不能读取未来通知。

到户核查和护送、物业任务竞争同一岗位。无法继续时可查看阻塞原因或改用电话；无回应可填写原因后结束本次核查，住户仍保持未确认。途中撤回先走完当前路段，保留位置后释放岗位，不瞬移到起点。核查人员到门、接收通知回执、安排居民行动是三个不同阶段。

电话、敲门结果仍由参演人员报告。系统只能确认仿真中的路径与到门状态，不以人物动画替代现场核验。

## 仿真与三维

新模式中，水源可用性与火势自然增长分开；“资源就绪”不直接压低火势。实际有效喷水才产生压制；断电、断气分别作用于对应场景，断电不等于电池火情解除。所有系数仍为明确标识的训练规则。

人物速度、路径估计和评分参考共用画像速度。现场详情显示训练户、画像与通知状态；原有脚下轮廓增加待通知、待确认的状态反馈，危险与拥堵颜色优先。定位复用服务端人物位置，并打开对应楼层的第三人称观察；第一视角仍需单独选择，没有增加占用通道的装饰几何。

## 工程与兼容

- `community_training` 冻结在创建事件的世界中；投影从事件重建，无浏览器私有成功状态。
- 场景参数为 `community_profile`、`duty_staff_count`、`simulation_seed`；缺省沿用旧规则。
- `20261113_task_kind` 为 `decision_tasks` 添加可空 `kind`。新标准任务保存明确类型；保存可编辑旧任务或复制新草稿时固定原语义。历史记录仍支持旧标题适配，冻结事件不改写。
- 引擎修订为 15，失效的派生检查点重建，旧场次不会因此启用社区画像或新环境规则。新冻结的社区契约为版本 2，增加到户核查与敲门到位条件；已冻结的版本 1 保留原人工回执兼容。
- 到户核查不进入起火房间，目标为冻结户门外的通行节点。烟气停靠阈值随社区世界冻结，属于训练规则，尚未经过实测标定。
- 新增行为复用 `participant.feedback` 和 `task.action` 入口、身份验证、命令及事件体系。
