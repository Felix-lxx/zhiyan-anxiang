# 场景自由配置与智能体架构升级规划

项目：智演安巷——面向老旧小区消防治理的数字孪生与智能决策平台
日期：2026-10-21
交付类型：基于现有代码的升级分析与实施规划；本文件中的新增能力为待实施设计。

## 1. 升级目标与范围

升级围绕一条可展示的产品主线展开：演练组织者选择案例和起火位置，调整人员及资源，创建冻结场次；智能体识别现场、生成可比较方案，经授权后组织真实行动；参与者在三维社区和手机端执行任务；最终查看预测与实际差异，并从同一起点重做。

首轮升级交付两个可运行案例：

1. **夜间充电棚火灾**：室外起火，主要训练通道处置、资源接近、跨楼栋疏散与机器人协同。
2. **住宅厨房起火与楼道烟气蔓延**：室内起火，主要训练房间—走廊—楼梯的风险变化、分层组织、有限护送资源及未到场人员查找。

两个案例共用地图、连续空间、指令、智能体、证据和复盘底座；通过场景策略形成不同规则和表现。两个用户端保持为组织指挥端、手机参演端，角色权限作为端内能力配置。

## 3. 整体架构

继续采用 Vue 3、Three.js、FastAPI、SQLAlchemy 和模块化单体。开发环境可使用 SQLite，多指挥员和持续运行部署优先 PostgreSQL。首轮不引入新的消息中间件或第三套状态存储。

### 3.1 模块与依赖

| 层次 | 建议模块 | 职责 |
| --- | --- | --- |
| API 入口 | `api/routes/scenarios.py`、`drills.py`、`agents.py` | 身份、请求映射、校验错误映射 |
| 应用服务 | `application/drill_commands.py`、`scenario_service.py`、`plan_service.py` | 事务、幂等、授权、领域调用、事件记录 |
| 场景领域 | `domain/scenarios/` | 模板能力、火源地址、任务生成、准备校验、冻结输入 |
| 演练领域 | `domain/drills/` | 居民、环境、资源、车辆、机器人及完成条件 |
| 智能体运行 | `agents/runtime/` | 目标、工作流、步骤依赖、授权、资源预占、恢复与观察 |
| 智能体能力 | `agents/capabilities/` | 感知、方案规划、资源协同、执行监督 |
| 基础设施 | `infrastructure/persistence/`、`realtime/` | ORM、事件读取、快照、租约、实时投影 |
| 前端功能域 | `features/scenarios/`、`director/`、`agents/`、`replay/`、`participant/` | 任务导向页面与局部状态 |
| 三维表现 | `three/world/`、`actors/`、`effects/`、`interaction/` | 基于权威快照绘制、选取、动画及降级 |

迁移按一个调用链完成一个闭环。旧入口保留薄适配器，期间不得复制两份寻路、评分或任务执行规则。目录移动与业务行为修改分批提交。

### 3.2 唯一权威与三类版本

- **场景版本**：准备配置、空间、任务规则、随机种子和模型参数的不可变输入。
- **场次状态版本**：事件序号与仿真时钟驱动的运行状态。
- **计划版本**：当前目标、方案、批准范围和执行步骤的修订。

智能体观察场次状态并提出方案；仿真引擎推进位置、环境和资源；应用服务应用已批准命令。所有前端和子能力读取同一场次状态。

不以每秒递增的状态版本作为所有方案一律失效的条件。批准校验同时检查观察起点和实际依赖：目标人群、相关路段、火源配置、可用资源与预计条件的变化；无关事件不强制用户重复批准。

## 4. 自由选择火灾位置

### 4.1 用户操作流程

1. 在案例入口选择充电棚或厨房案例。
2. 打开“起火位置”，三维现场只高亮该案例允许的目标。
3. 室外案例点选充电棚或允许的场地；室内案例依次选建筑、楼层、房间，并进入该层剖面。
4. 点选后显示火源标记、空间地址、受影响区域和可通行道路，提供“撤销本次选择”。
5. 调整起火时刻、初始强度、门状态、人员和资源；预览阶段不写入运行命令。
6. 准备检查给出具体对象和字段；点击缺项定位回原位置。
7. 确认本次配置后创建新场次，并冻结运行输入。

键盘、对象列表与楼层列表提供与三维点选等价的入口。演练者可在不操作视角的情况下完成配置。

### 4.2 权限与修改时机

默认由组织指挥端的创建者选择火点。若训练需要手机参演者自主选题，组织者授权某个参演会话提交火点提议，提议只引用允许的对象和房间，确认后才创建场次。权限绑定当前场次及会话，沿用两个端。

准备期间可以改点、撤销和重新预览；运行中主火源保持冻结。运行中的“新增起火事件”与“从历史创建另一火点分支”是两种独立操作，后续若开放必须使用新事件或新分支，不能拖动已有火点重写已发生的风险和人员历史。

首轮实现一个可配置主火源；数据结构预留火源标识，但不同时交付多火源耦合。

准备、教学引导与正式考核共用该机制：教学模式可完整显示火点；考核模式可由获授权人员选定后隐藏具体火点。智能体感知和手机任务读取各自允许的观察投影，不能因掌握服务器真值而提前获得尚未发现的位置。

### 4.3 统一火源地址

建议 `FireSourceSpec` 包含：

| 字段 | 用途 |
| --- | --- |
| `source_id`、`scenario_kind` | 火源及案例身份 |
| `location.kind` | `object`、`room` 或后续受控的 `ground_zone` |
| `location.object_id` | 所属充电棚、建筑或场地 |
| `location.floor_id/room_id/zone_id` | 室内所在空间，均须属于冻结版本 |
| `location.local_position` | 房间内受约束的选点，服务端推导世界坐标 |
| `ignition_at_seconds` | 相对本场演练时钟的起火时刻 |
| `initial_intensity`、`growth_profile` | 初始状态及规则参数版本 |
| `boundary_state` | 已建模的门、连通边等初始条件 |

坐标只是地址的投影，不是唯一身份。不得接受“位于任意楼层的任意 x/y”作为合法室内火源。准备预览、冻结事件、运行、复盘、分支和模型特效共用该地址。

火源配置错误直接给出可定位的校验结果；旧场次通过版本适配器读取原二维火源，新场次不采用默认充电棚回退。

原有“20:15”属于案例背景时刻；`ignition_at_seconds` 属于仿真时钟。界面分别显示“演练开始时刻”和“开始后多少秒起火”，冻结时统一换算，避免把背景时间当作起火倒计时。暂停冻结仿真时钟，业务等待和暴露随该时钟推进；网络超时、工作进程租约使用服务器实际时间。

### 4.4 模板能力声明

模板应显式声明可用火源类型、可选空间、必需资源、支持任务、环境策略、完成条件和显示方式。创建页、发布校验和场次冻结均消费同一份能力声明。

例如，厨房案例允许 `room` 火源、需要有效室内连接、支持分区烟气和楼层剖面；充电棚案例允许 `charging_shed` 火源，优先显示室外风向、道路、水源与接近路径。模板默认参数统一命名，收束现有 `time/start_time`、`wind/wind_direction` 的混用。

## 5. 第二场景：住宅厨房起火与楼道烟气蔓延

### 5.1 可落地的演示内容

选择社区中的一栋既有住宅，先完成单栋、多个楼层、一个起火房间的精细示范。其他楼栋继续由现有社区模型承载，随后扩展到多栋室内场景。

| 模块 | 充电棚案例 | 厨房案例 |
| --- | --- | --- |
| 起火空间 | 充电棚及周边室外区域 | 具体楼层和房间 |
| 主要风险 | 接近道路、室外暴露、资源失效 | 起火房间、走廊、楼梯的分区风险 |
| 主要可操作对象 | 道路、水源、车辆、机器人、人群 | 楼层、房间、通道边界、人群、值守员 |
| 机器人行动 | 沿路到楼门巡检或广播 | 在实际可通行的楼外/门厅位置行动 |
| 护送任务 | 到楼栋会合并同行至集合点 | 根据楼层和通道可达性组织会合 |
| 结果 | 疏散、资源处置和清点 | 分区响应、未到名单、护送及清点 |

厨房场景的差异体现在风险变化和行动约束。机器人是否能上楼由实体能力和通道规则决定，未建模爬楼能力时不生成上楼任务。

### 5.2 室内风险模型

采用可解释的“房间—走廊—楼梯—门厅”分区图。每个分区维护烟气负荷、可见度代理量和风险等级；连通边描述门状态、交换系数和通行条件。仿真按固定时间步传播，计算通道风险、人员暴露和路径代价。

实施要求：

1. 从现有连续空间图生成稳定的分区 ID，明确节点、边和模型几何的映射。
2. 明确地图水平单位和楼层高度单位；将现有 0–100 归一化坐标通过冻结比例转换为一致空间单位，避免用不等尺度的平面坐标和高度计算风险距离。
3. 火源起火前保持初始环境；起火后按模型参数推进，不把全场经历时间直接当作燃烧时间。
4. 每个时间步使用同一时刻的分区状态计算人员暴露，避免室外烟气半径与室内风险重复计量。
5. 改门状态同时影响烟气交换和通行规则，分别定义两个效应，不能用同一个布尔量代替所有变化。
6. 预演和正式运行调用同一模型；分支复制分区状态、人员队列、动作剩余时间和随机状态。

第一版使用标注为规则模型的风险代理量，参数与版本可追溯。不会把代理值直接包装成经过物理校准的烟气浓度或真实温度。

车辆喷水同样需要场景能力检查：室内火源的高度、可达作业面和允许的施救接口必须参与判断。首轮厨房案例若尚未实现室内供水/射流作用，车辆到场只更新其已实现的支援任务，不直接降低任意楼层的火势。

### 5.3 人员与任务闭环

保留居民连续移动，新增室内位置与分区风险详情；任务采用显式 `task_kind` 和目标地址，逐步消除通过任务标题包含“断电”“广播”等关键词推断业务类型的路径。

居民因通道不可达进入明确等待/求助状态，继续记录实际位置与风险。等待协助地点必须是地图中配置的有效位置。护送须经过资源分配、到目标会合、同行和到场步骤。场景完成条件分别统计到场、清点、未到场及处置证据，未满足条件不能通过更换模板或改目标而消失。

场景任务内容由已验证的规则模板配置，现场行动限制通过服务端执行；具体消防处置策略的扩展需有明确的业务依据。

## 6. 智能体架构与编排

### 6.1 一个协调器、四种能力

| 组件 | 输入与输出 | 可调用能力 | 完成依据 |
| --- | --- | --- | --- |
| 协调器 `IncidentOrchestrator` | 目标、观察版本 → 可批准方案和运行图 | 读取能力结果、控制计划修订 | 全局目标条件与任务证据 |
| 现场感知能力 | 权威快照及增量 → 风险、对象、缺失信息 | 只读空间、资源、事件 | 结果附观察序号和对象引用 |
| 方案规划能力 | 目标、约束及观察 → 候选方案与预演 | 路径、分流、预测工具 | 可执行性、代价及覆盖范围 |
| 资源协同能力 | 方案步骤、资源池 → 分配、依赖和等待条件 | 值守员、机器人、车辆资源检查 | 唯一资源预占和真实回执 |
| 执行监督能力 | 命令回执及现场变化 → 异常、重规划请求、结果核对 | 进度、证据、预测对照 | 实际事件、位置和完成条件 |

这四种能力先以进程内、可独立验证的模块运行。语言模型承担目标理解、受约束的方案草案和解释；路径、资源合法性、空间移动和评分由确定性工具提供。后续只有出现明确收益时才为某项能力配置独立模型调用。

### 6.2 编排任务与工作流的关系

系统接收的是目标，例如“组织 3 号楼重点人员疏散，并保障楼门广播”。协调器据此选择已注册的工作流，并生成任务依赖图。

工作流负责阶段与规则：观察 → 方案比较 → 人工批准 → 调度 → 执行监督 → 结果核对。任务图负责本次具体对象：哪批居民走哪个出口、哪名值守员护送谁、机器人到哪个点、何时允许广播。

依赖图允许并行：居民分流与机器人前往广播点可同时执行；广播依赖机器人真实到位；第二批护送依赖人员资源释放；清点依赖实际到场并由参演人员核验。

首轮注册两种案例工作流，复用已有步骤，不让模型自由发明工具、任务类型或完成条件。

### 6.3 计划与步骤契约

每个步骤保存：`step_id`、`plan_revision`、`command_id`、工具名称和契约版本、目标地址、前置步骤、读取依赖、资源请求、预计时长、当前状态、重试策略和完成证据规则。

步骤状态建议为：`pending`、`ready`、`awaiting_approval`、`accepted`、`executing`、`blocked`、`completed`、`failed`、`cancelled`。`blocked` 保存可解除的具体原因；失败记录领域错误码。超过预计时长进入监督检查，不能仅依赖时间自动完成。

自然语言目标保存原文和结构化解释；候选计划保存对哪些对象、资源和动作申请授权。模型输出必须通过契约和对象白名单校验。

确认页明确批准的对象、动作和资源上限。单纯重复投递同一技术请求沿用授权；扩大目标人群、增派车辆、变更关键路线或提高资源占用等实质变更，生成新的批准版本。只读定位、证据查询和状态解释无需重复确认。

### 6.4 资源竞争与人工接管

- 资源预占以场次为边界，覆盖所有账号的活动计划，而非仅检查当前账号最新计划。
- 机器人单机任务、值守员岗位和车辆服务有唯一执行归属；批量分配在同一事务中完成。
- 预演只估计可用资源，不占用资源；批准时重新检查，冲突则展示具体被占用资源和修订方案。
- 抢占只允许显式人工操作；先停止后续自动下令，再确定已接受任务如何继续或取消。
- 人工改派创建新的执行归属版本。旧计划的后台监督只能继续读结果，不能再次抢回控制。
- 技术重试复用原命令 ID；业务重规划生成新的计划版本。持续移动的实体接续位置和路径，不重复扣电、重置暴露或制造第二名护送员。
- 取消后释放未开始的预占；在途资源在任务真实结束或显式取消完成后释放。租约过期与计划崩溃通过恢复任务回收，不能直接当作动作完成。

### 6.5 触发和恢复

道路封锁、关键分区风险变化、资源失效、任务失败和人工接管触发相关计划检查。事件到计划依赖有索引，短时间重复变化合并处理；同一计划只保留一个待执行重规划请求，防止反复弹确认框。

常规状态更新继续复用现有实时通道。持久命令、任务、事件与观察任务作为恢复依据；重启后从已提交步骤接续。后台所有者与修订版本共同作为写入条件，避免过期工作进程继续下令。

## 7. 系统联动与契约

### 7.1 自由火点的端到端链路

火点选择保存 → 模板能力校验 → 冻结场景和单位比例 → 创建场次 → 火源在指定时刻激活 → 分区与路段风险变化 → 居民和机器人规划变化 → 监督提示 → 人工批准修订 → 命令执行 → 证据、评分与复盘。

火点的三维特效、机器人巡检目标、车辆处置目标、环境风险和任务位置必须从同一个冻结地址派生，不分别维护坐标。

### 7.2 建议接口

| 接口意图 | 必需行为 |
| --- | --- |
| 读取场景能力 | 返回允许火源空间、参数、任务与渲染能力 |
| 保存草稿配置 | 返回具体字段校验和对象定位信息；版本冲突可恢复 |
| 场景预览 | 只读、可取消，标识输入哈希、模型版本和预演时刻 |
| 创建场次 | 固化场景版本、种子、火源地址和规则版本；支持请求幂等 |
| 创建目标/比较方案 | 返回可执行候选、资源冲突、完成条件和观察起点 |
| 批准/修订计划 | 同时检查计划版本、实际依赖和执行资源 |
| 获取活动计划 | 场次范围内按权限返回活动列表，自己的私有解释独立控制 |
| 查询结果核对 | 保留原预测与对应观察时刻，能够定位三维复盘 |

事件最少包含：场次 ID、事件 ID、递增序号、仿真时间、类型、对象引用、操作者、命令关联和因果引用。广播在事务提交后读取持久事件；断线继续使用事件游标和快照补偿。现阶段沿用已提交事件的读取机制，只有引入异步外部通知时再增加事务型 Outbox。

## 8. 页面升级与布局规则

沿用浅色资料工作台与深色三维导演台的视觉体系。按 Impeccable 的 Operate/Experience 场景组织信息：准备页服务于配置任务，导演台突出空间行动，复盘页服务于解释差异。

| 页面 | 主内容与布局 | 必须可完成的操作 |
| --- | --- | --- |
| 演练入口 | 两个案例预览 + 最近活动；内容按可用宽度排布 | 选择充电棚/厨房、续练、复制并配置 |
| 场景准备 | 左侧步骤、中间三维、右侧当前步骤参数 | 选择火点、楼层/房间、人员、资源并定位缺项 |
| 三维导演台 | 顶部状态、中部现场、单个侧栏、底部紧凑时间线 | 点选操作、预览、批准、观察和恢复 |
| 智能体工作区 | 任务目标、方案、执行、依据与结果核对 | 清楚看到为什么、何时执行、谁被占用、哪里受阻 |
| 室内剖面 | 当前楼层空间、烟气分区、人物队列 | 切层、定位房间、查看等待原因和可达路径 |
| 手机参演 | 当前负责事项优先，按接受/到位/证据组织 | 独立回执、异常上报、集合清点 |
| 复盘比较 | 同步视角的双世界 + 同批人员对照 | 回到决策时刻、另选方案、比较相同观察窗口 |

### 8.1 导演台的空间管理

引入统一工作区状态，例如 `scene`、`selection`、`preview`、`agent`、`tasks`、`replay`。助手、任务、预演和对象详情由同一控制器切换；避免继续增加相互独立的布尔开关与绝对定位浮窗。

常驻信息保留演练状态、时间、连接、关键风险和当前目标。火点编辑只出现在准备状态；动作详情出现在选中对象后。智能体状态展示实际任务和等待依赖，不用聊天消息模拟执行完成。

执行按钮附近显示受理回执和执行对象；用户不必再次打开证据页才能确认是否开始。完成后提供结果核对与历史定位入口。

### 8.2 尺寸与阅读

- 正文与主要操作 16px，辅助信息 14px，大字模式继续支持；触控目标至少 44px。
- 宽屏三维占主区域，侧栏跟随工作区占位；主要侧栏建议 360–440px，由容器宽度决定。
- 低高度屏幕缩短常驻时间线、压缩工具文字，侧栏独立滚动，操作不靠缩小字号适配。
- 平板以单个侧栏或底部面板展示；手机采用现场/任务/助手切换，空间预览后返回现场。
- 对话输入、抽屉标题和确认操作分别有明确布局位置，长内容滚动区域位于中间。
- 空状态仍展示案例、示例动作或配置缺项；避免左右等高占位导致单侧长列表与大片留白。

## 9. 三维建模与可视化

模型升级先补影响任务理解的空间结构，再提高装饰精度。

1. **统一空间真值**：建筑轮廓、门洞、楼梯、房间、道路与集合点来自共享布局，碰撞轮廓与实际通行图一起版本化。
2. **厨房场景结构**：补厨房、门、走廊、楼梯平台和门厅；关门/开门有明确铰链和通行状态，剖面切层不改变服务器可达性。
3. **可观察人物**：会合、等待、转向、同行状态复用现有角色动画。移动沿服务端路径折线，视觉插值不能跨过墙体或封锁边。
4. **空间风险表现**：室外显示路段风险，室内显示分区烟气/可见度；火源具有正确高度及地址标签。门后烟气不能简单画成穿墙透明球。
5. **真实调度表现**：机器人展示当前任务和下一步条件，车辆展示停车与作业区域；实体尺寸、转向空间和通行检查一致。
6. **性能分层**：静态物体合批/实例化；人物远景实例、近景骨骼；室内按选中建筑和楼层加载；不同画质使用相同运行状态和对象 ID。
7. **资源可交付**：资产本地托管、记录来源许可、比例、面数和加载失败替代；精细资产未就绪时仍能选择对象和完成任务。

先以现有 60 人演示场次和 300 人扩展示例观察性能；1000 人保持为容量目标，经现场剖析后确定可支持的细节等级，不把当前参数上限直接当作流畅性能承诺。

## 10. 数据与仓库升级

### 10.1 数据演进

按阶段引入场景能力、室内布局版本、计划步骤和资源预占。可复用的现有实体包括 `SceneTemplate`、`SceneVersion`、`AgentRun`、`DrillCommand`、`DrillEvent`、`AgentDecisionCheck`。

建议新增或演进：

- 场景定义的 `schema_version`、规则版本、模板能力、火源地址和输入哈希。
- 冻结世界中的地图单位比例、分区、空间连接和随机状态。
- `agent_plan_steps`：依赖、命令、状态和完成条件；先兼容现有 JSON 步骤，单个计划一次只用一种执行存储。
- `resource_reservations`：场次、资源、计划步骤、归属版本、有效状态及恢复期限，活动预占有数据库唯一约束。
- 保留已有结果观察表，每个批准版本绑定同批居民、预测起点和实际观察时刻。

新结构采用迁移脚本，支持已有数据库升级；演示数据使用可重复运行的种子，不覆盖用户社区。旧场次始终按旧引擎/规则版本回放。

### 10.2 仓库组织

根 README 只保留产品能力、两个案例、操作入口、安装启动、模型配置和当前限制；长变更记录转入 `CHANGELOG.md` 与日期文档。架构文档记录当前结构，升级规划标明计划状态。

整理内容：

1. `docs/architecture/` 保存模块边界、命令链、场景契约、智能体任务契约和迁移策略。
2. `docs/scenarios/` 分别记录两个案例的配置、任务和演示步骤。
3. `docs/decisions/` 或现有 ADR 目录记录重要取舍，沿用一种目录约定。
4. `backend/tests/` 按场景、命令、智能体、安全和实时分组；前端布局脚本保留隔离夹具。
5. `assets/manifest` 记录模型与贴图许可、尺寸、版本和轻量替代，依赖离线可用。
6. CI 保留固定运行环境、隔离数据库、前端类型与构建；密钥、数据库、运行日志和截图产物不进入源码提交。
7. 一个提交围绕一个可回退的能力，目录迁移不与引擎语义改写混在同一提交中。

## 12. 适度验证与持续自审

验证围绕改变的规则和一次真实演示组织：契约变更检查冻结一致性；执行变更检查幂等与资源互斥；厨房环境检查同起点可重现；页面变化批量检查桌面、短屏、手机。每个阶段复用现有脚本，问题修复后确认一次，不进行无目标反复测试。

交付前保留五条验收主线：

1. 选不同火点 → 新场次风险、巡检和任务位置随之改变。
2. 房间起火 → 分区变化 → 通道风险 → 人员排队/改道 → 集合清点。
3. 两个计划竞争同一资源 → 只接受一个归属，另一个显示可解释等待。
4. 人工改派/断线/进程重启 → 已受理任务连续，旧计划不能夺回控制。
5. 同一历史快照、同一批居民、同一观察窗 → 两种选择的证据和结果可比较。

## 13. 自我拷问与设计修正

| 自问 | 发现的漏洞 | 规划中的修正 |
| --- | --- | --- |
| 两个模板能列出来，第二场景就可用了？ | 配置和校验仍锁定充电棚 | 按案例能力贯通准备、冻结、环境、任务和渲染 |
| 允许任意点选是否就是自由度？ | 可能把火点放在墙内或不属于该楼层 | 以合法空间地址选择，局部点位受边界约束 |
| 演练中拖动火点是否简单方便？ | 已发生的暴露与任务可能被重写 | 主火源冻结，另案使用事件或分支 |
| 四个状态栏目是否等于四个智能体？ | 缺少独立契约、执行输入和失败归属 | 建立四能力接口与统一协调器，展示真实调用与结果 |
| 每个智能体用一个模型是否更强？ | 延迟、冲突、重复下令增加 | 模型只在适合的理解/解释环节调用，规则工具计算事实 |
| 每次状态版本变化都让方案失效是否可靠？ | 时钟每秒变化导致用户无法批准 | 依赖级校验、有限有效期和提交前资源校验 |
| 预演使用资源是否应立即占用？ | 仅浏览方案即可阻塞其他计划 | 预演只估计，批准后事务预占 |
| 服务重启后重发指令能否恢复？ | 可能重复派机器人、扣电或生成护送员 | 持久步骤、稳定命令 ID、归属修订和已受理动作恢复 |
| 厨房只把火焰抬高是否足够？ | 风险仍会隔墙传播到错误楼层 | 分区环境和有效连接控制传播与通行 |
| 3D 细节真实就不会穿模？ | 模型轮廓与图可能来自不同数据 | 布局、碰撞、渲染共享空间版本和通道身份 |
| 不同运行窗口的结果能直接比较？ | 时长、人口和随机状态不同会误导 | 冻结同起点、种子和人口，以相同观察窗比较 |
| 大目录移动是否代表架构升级？ | 调用方向和规则重复可能保持不变 | 先迁移调用链，再移动目录；可适配、可回退 |

最终交付以两个案例都能完成“选择—行动—变化—核对—重做”为准；智能体界面应能回答当前目标、依据、执行对象、等待原因和下一次需要人确认的地方。
