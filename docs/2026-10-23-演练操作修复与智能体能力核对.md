# 演练操作修复与智能体能力核对

## 修复对应关系

| 实跑问题 | 实现 | 可观察行为 |
| --- | --- | --- |
| 厨房新场次名称变成充电棚 | 新场次默认取当前场景名称，切场景清除旧输入 | 厨房新一轮仍保留厨房案例名称 |
| 审阅时间导致方案过期；暂停不能批准 | UI提交 `pause_for_review`；服务端暂停、冻结仿真时间，允许暂停批准后继续 | 阅读方案期间人员、烟气和任务倒计时不前进；批准后恢复 |
| 人工处置脱离目标计划 | 任务图投影案例责任任务、前置条件、核验状态与倒计时；新UI启用 `include_case_tasks` | 助手能指向待处置任务；居民到场不再提前宣告完整案例完成 |
| 相同出口分配缺少实际替代动作 | 厨房增加“撤空后关门控烟”候选和真实 `indoor.door.set` 步骤 | 分流并行推进；房内、门洞或护送员占用时等待，撤空后执行；产生领域证据 |
| 待完成0被误解为全部任务完成 | 指令过滤改名“运行中指令”；任务抽屉分别列任务、指令、清点人数 | 任务与指令有独立计数 |
| 集合清点入口深 | 态势按钮直接进入统一清点抽屉，助手与任务入口复用同一抽屉 | 逐人勾选实际到场居民，确认后更新服务端、评分和智能体；未到场仍不能清点 |
| 长场次读锁造成断连、重复提交疑虑 | 后端慢读取保留单个读任务并发送传输心跳；客户端45秒失联判定、HTTP补读；HTTP命令超时后核对原命令回执 | 传输存活不冒充状态新鲜；补读不污染增量流基线；原命令编号保持幂等 |
| 首次训练时限过短 | 新场次支持教学/考核；教学按任务类型设置最低时限 | 教学：电源240秒、燃气300秒、房门420秒、广播360秒、护送600秒；考核沿用发布参数 |

教学模式仅修改新场次冻结世界，保留场景原定时限用于追溯。没有对已结束的55分场次补分。时间预算属于训练配置，不代表现实消防处置时间标准。

## 智能体是否名副其实

恰当名称是“人工批准的、仿真驱动的疏散协同智能体”。现有实现具备以下连续控制链：

1. 根据自然语言或明确楼栋/居民范围得到目标约束；模型解析可选，离线解析明确标注。
2. 读取服务端现场事实、连续空间图、烟气、队列、人员和资源。
3. 根据路径、风险与容量产生分配，使用相同仿真引擎预演，并合并等价动作。
4. 人工批准后编译持久化依赖图，登记机器人、居民、值守员和房门资源归属。
5. 通过统一命令应用服务执行分流、护送、移动、广播及安全门控。
6. 以实际到达、会合、广播、门状态和核验证据监督任务；受阻请求修订，人工接管让出控制；进程恢复复用命令编号。
7. 核对预测与实际结果，最终要求人工责任任务和集合核验完成。

因此“智能体”可以成立，但“四个独立自主智能体”会夸大实现：感知、规划、资源、监督是一个协调器内的四类能力，不是四个大模型自主讨论。大模型当前主要参与目标理解与解释，确定性规划器和仿真引擎负责具体动作与合法性。

系统没有在线学习或自主修改评分规则。控烟候选的预测仅覆盖所标明的30秒窗口，门洞仍占用时不会把关门收益算入该窗口；不能承诺一定比另一路线得分高。燃气和电源操作继续由责任人回执并提交证据，智能体监督不等于系统亲自在现实中完成处置。

## 自我追问

- 有没有通过放宽考核标准抬高旧成绩？没有。教学预算只冻结进新场次；考核保持原配置。
- 有没有把文字提示当作执行？没有。房门候选通过原命令服务执行；安全前置校验和事件证据仍有效。
- 有没有把四个标签包装成多智能体？没有。界面交代解析、规划、批准、执行和核对的实际职责。
- 有没有让清点绕过到达条件？没有。前端逐人选取，服务端继续校验实际到场。
- 心跳恢复是否等同于性能问题已消失？不是。它解决慢读时的误断线和补偿，仿真与数据库负载还需要按实际规模持续观察。
