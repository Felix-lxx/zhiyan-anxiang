# 车辆调度与实体增量同步

## 本轮交付

围绕上轮留下的大人口同步、静态车辆和重复预演请求三个断点改造。维持现有导演台信息架构，不增加仪表盘或并行浮窗。

### 1. 实体级增量同步

协议 3 对居民、护送员、车辆按 ID 对比，只传新增、移除及变化字段；顺序改变时附带顺序列表。如果增量比完整列表更大则发送列表。静态路线和未变化对象保留前端引用。现有协议 1/2 不变。

前端拒绝缺失实体、重复 ID、非法字段和不连续版本，沿现有重连机制重新获取权威快照。三维主更新监听不再深度遍历整个人口与冻结模型。此改动减少传输与响应式遍历，不等于仿真内核已做到所有计算增量化。

千人单字段变化测试验证：增量体积低于完整状态的 1%，且只包含该居民的变化字段。这是稀疏变化工况，不是全体居民运动时的吞吐或帧率承诺。

### 2. 车辆调度闭环

入口：启动演练 → 底部处置任务 → 应急车辆；也可点击三维中的车辆进入调度。

1. 选择消防车或救护车，选择本场冻结路网中的到场节点。
2. 预览路线、路线长度、风险和预计时间。预览不移动任何对象。
3. 确认后由统一命令入口记录指令；重复传输沿用同一 command_id。
4. 服务端依演练时间推进车辆。前端插值只到服务端确认位置，不自行推演。
5. 封路或恢复道路同时触发车辆重新规划。在已封闭路段中的车辆保持原位，不跳到最近节点穿越障碍。
6. 可手动重新规划或取消行程；取消后保留当前位置。到达后记录 vehicle.arrived，更新指令完成状态。
7. 刷新从冻结地图和事件恢复；历史回放使用当时时间；创建分支重映射行程和命令证据引用，避免关联原场的事件 ID。

规划使用带风险与拥堵权重的最短路，过滤封锁及宽度不足的道路。消防车/救护车的宽度和速度为当前场景参数。单车一次执行一个行程；有活动行程时拒绝重复派车，并提示取消或重算。

模型沿用已入库的 Kenney firetruck/ambulance GLB，独立异步加载，15 秒超时，卸载中止请求并释放模型资源。基础模型始终保留真实位置和点选能力，因此资源失败不阻塞现场。

### 3. 统一预演请求

新增 useDrillPreview，空间指派与训练教练共用：15 秒超时、主动取消、场次标识校验、暂停/复盘时失效、组件卸载清理。取消只作用于只读预演，不中止已经提交的命令。提交失败不显示成功，冲突后只有真正生成新预览才提示“已重新生成”。

### 4. 界面

车辆调度进入现有互斥任务抽屉。打开路线预览后关闭抽屉，沿用统一视口避让，避免遮挡确认按钮和时间线。表单、按钮和状态采用现有深绿令牌；正文 16px、说明 14px、按钮至少 44px，窄屏自动换行。车辆到场和预计耗时显式展示，暂停时注明冻结。

## 有限验收

- 前端类型检查及生产构建通过。
- 3 项车辆/人口针对性测试通过：逐段移动、宽度约束、封锁停止与恢复、幂等指令、持久化、到场事件、回放与分支，以及千人稀疏增量。
- 既有双客户端封路同步与重连测试通过，旧协议仍可用。
- 前端实时消息和指令重试 10 项测试通过。
- 隔离浏览器检查 1440px、390px：车辆模型请求 200，无浏览器运行异常，任务抽屉无横向溢出；人工查看截图确认字段与按钮留白。该检查没有修改用户数据库，也不代表所有页面完成视觉回归。

## 自我拷问与下一优先级

- **是否仍是静态车辆换皮？** 不是：位置、行程状态、封路重算、回放与指令回执来自同一事件投影，GLB 只负责表现。
- **是否把出车当救援完成？** 没有：只生成到场证据，不自动完成灭火、伤员转运任务或增加分数。
- **是否解决了所有大人口性能问题？** 没有：本轮是实体传输和监听优化；长历史投影、全部人员持续移动和低配显卡仍需按真实工况分析。
- **是否取消预演就取消了现场指令？** 不会。请求层区分只读预演与幂等命令，关闭面板不改变已经受理的操作。
- **还有哪些联动不完整？** 车辆目前读取道路拥堵用于规划，不反向占用居民道路容量；尚无车人避让、会车、转弯半径和停车占道模型。下一轮优先实现车辆到场后的任务前置条件及道路占用，再做灭火供水/伤员装载的业务闭环。
- **还有哪些建模问题？** 当前沿道路中心线逐段移动；狭窄道路与路口的车体扫掠范围尚未纳入规划，需要用车长、轴距与转弯半径约束解决，而不是继续增加装饰模型。

本轮没有推送 GitHub，没有改写用户既有场景、场次或账号配置。已使用原 SQLite 数据库重启 API，健康检查 healthy，新车辆预演接口已出现在运行中的 OpenAPI；前端开发模式由 Vite 自动更新。打开的页面可刷新后进入「处置任务 → 应急车辆」。
